# Before/after: what ordinary logging shows vs. what receipt-view shows

Three concrete tampering cases against the same recorded agent episode
(a two-step tool-using run: the model calls a `calc` tool, gets a result,
then produces a final answer). Each case mutates exactly one field in the
committed receipt file and compares two things side by side:

- **"ordinary logging"** — the receipt's own claimed fields as printed by
  `receipt-view.py`'s `WHAT RAN` section. This section is generated by a
  function the tool's own source explicitly documents as "best-effort
  display only... NOT a validating parser" (`receipt-view.py`,
  `parse_receipt()` docstring) — it just reads whatever text is in the
  file and prints it. This is the same class of information an ordinary
  print-based or JSON execution trace would record: text that could have
  been typed by anyone, with no independent check that it corresponds to
  anything that actually happened inside the model.
- **what receipt-view shows** — the `HASH CHAIN` section, which does not
  trust the receipt's own text at all. It shells out to `agent_trace
  verify` (the real verifier, `aegis-linux/examples/agent_trace.rs`),
  which independently *replays* the episode against the pinned model /
  embed / vocab artifact files and recomputes each step's chained digest
  from scratch. `receipt-view.py` only reformats that verdict as prose —
  it does not hash or replay anything itself.

All three receipts below are single-field mutants of one baseline,
`good-receipt.receipt` (INTACT, verifies), documented and committed in the
`alice-aegis` repo at `demo/agent-trace/receipt-view-fixtures/` and its
`receipt-view-README.md`. Commands and output below were re-run for this
document rather than copied from that README, to get exact output for
every case (the README itself only shows the baseline and case (b)
verbatim; this doc adds (a) and (c)).

**Setup used for all three:** BitNet-2B pruned checkpoint artifacts at
`~/aefinity-artifacts/bitnet2b-2b-artifacts` (sha256: model
`facb3597...45868db`, embed `e32b99a2...4d364e077`, vocab
`5bde1b03...c2d97d9ae` — not checked into either repo, referenced by hash
only), `agent_trace` built from `alice-aegis` commit `d9165c0` (a read-only
worktree of `origin/main`), run on host `aefinity-box`, 2026-09-22.

```
demo/agent-trace/receipt-view.py demo/agent-trace/receipt-view-fixtures/<file>.receipt \
    --model <bitnet2b>/aegis_pruned_model.cis.safetensors \
    --embed <bitnet2b>/embed.bin --vocab <bitnet2b>/vocab.bin \
    --bin <alice-aegis>/aegis-linux/target/release/examples/agent_trace
```

## (a) Changed token

**What was mutated:** in `m1-changed-token.receipt`, step 0's first
decoded token id was changed from `34007` to `34008` (one id, one step,
everything else byte-identical to the baseline receipt). This token is
internal model output preceding the visible `CALC(...)` tool-call text —
it does not appear anywhere in the tool call itself, the tool's
input/output, or the final answer text.

**What ordinary logging shows:** identical to the baseline, because the
`WHAT RAN` view never prints raw token ids, only the tool call and its
decoded input/output:

```
  2 step(s) recorded in the receipt:
    step 0: 16 token(s) decoded, tool=calc, called 'CALC(10 + 10)' -> '20'
    step 1: 16 token(s) decoded, tool=no-tool
```

This line is byte-for-byte the same whether the receipt is
`good-receipt.receipt` or `m1-changed-token.receipt`. Nothing in an
ordinary "what did the agent do" trace log would ever surface this
mutation — there is no field in that kind of log for a raw intermediate
token id.

**What receipt-view shows:**

```
HASH CHAIN
  BROKEN — agent_trace verify rejected this receipt.
  First broken step: step 0
  What changed at that step:
    - the step's token ids
  (verifier line: step 0 divergence: toks-match=false tool-match=true in-match=true out-match=true decode-chain-match=true)

VERIFIED OFFLINE: yes — the check ran fully offline and correctly
rejected this receipt (see HASH CHAIN above).
```

`agent_trace verify` replayed step 0 against the pinned model artifacts,
recomputed the actual token ids the model produces for that step, and
found they don't match what the receipt claims — even though the tool
call, its input, its output, and the decode-chain digest all still agree.
Exit code: 1.

**Backing artifacts:** `alice-aegis` `demo/agent-trace/receipt-view-fixtures/m1-changed-token.receipt`
and `good-receipt.receipt`, verified via `demo/agent-trace/receipt-view.py`
against `alice-aegis` commit `d9165c0` on host `aefinity-box`, 2026-09-22.

## (b) Flipped intermediate logit bit

**What was mutated (single-fixture case):** in
`m3-flipped-bit-decode-chain.receipt`, one bit was flipped in step 0's
`decode-chain=` field (the per-step chained digest over the model's own
decode state) — the last-nibble bit-flip changes the field's final hex
character from `...e0eb` to `...e0ea`. Every other field (token ids, tool
call, tool input/output) is untouched.

**What ordinary logging shows:** identical to baseline, because the
`WHAT RAN` view never prints the decode-chain field at all:

```
  2 step(s) recorded in the receipt:
    step 0: 16 token(s) decoded, tool=calc, called 'CALC(10 + 10)' -> '20'
    step 1: 16 token(s) decoded, tool=no-tool
```

This is the strongest of the three cases: the receipt's own printed
step line is byte-identical to the untampered baseline. There is no field
an ordinary trace log records that this mutation touches at all — the
tampering is entirely inside a value that only exists to be checked, not
to be read.

**What receipt-view shows:**

```
HASH CHAIN
  BROKEN — agent_trace verify rejected this receipt.
  First broken step: step 0
  What changed at that step:
    - the step's decode-chain digest (the model's own chained decode state for that step)
  (verifier line: step 0 divergence: toks-match=true tool-match=true in-match=true out-match=true decode-chain-match=false)

VERIFIED OFFLINE: yes — the check ran fully offline and correctly
rejected this receipt (see HASH CHAIN above).
```

**Backing artifact:** `alice-aegis` `demo/agent-trace/receipt-view-fixtures/m3-flipped-bit-decode-chain.receipt`,
verified via `receipt-view.py` against commit `d9165c0` on host
`aefinity-box`, 2026-09-22 (same run as case (a); also reproduced verbatim
in `alice-aegis` `demo/agent-trace/receipt-view-README.md`, "Mutation test
(4 cases)").

**How this generalizes beyond one fixture (aggregate numbers, not
re-measured here):** the single-bit-flip case above is a hash-chain-field
mutation, not a model-weight bit flip; the closest weight-level analogue —
flipping single bits inside the model's own weights and asking whether
the resulting change in the model's actual internal computation (its
logits) gets caught — was measured separately and at scale in
`cis2-spec/docs/results/2026-09-13-BITFLIP-HEADTOHEAD.md`. In that
experiment (295 single-bit weight flips, stratified by tensor class, on
the same pruned BitNet-2B checkpoint), of the 247 trials where the flip
actually changed the model's output (logit-changing flips):

| check | misses / 247 logit-changing flips |
|---|---|
| text/argmax replay (comparing only the printed output text) | 182 / 247 |
| top-k / receipt-style check (a cheaper, coarser logit-set comparison) | 82 / 247 |
| CIS witness digest (full-logit cryptographic chain) | 0 / 247 |

(`2026-09-13-BITFLIP-HEADTOHEAD.md` section 3, "Aggregate miss rate among
all 247 logit-changing trials"; underlying raw counts and Wilson CIs cited
there back to `state/reports/2026-09-13-moat3b-stratified-box1.md` and
`state/reports/2026-09-13-moat3b-verify.md` in the private ops repo, not
re-derived here.) In plain terms: comparing only the final printed text
missed most (182/247) of the cases where a single flipped weight bit
demonstrably changed what the model actually computed; a cheaper
logit-set check caught more but still missed a third (82/247); the
cryptographic digest over the actual computation caught all of them
(0/247). That experiment also found 43 flips that produced no output
change at all under any check — a correct non-detection, not a miss (see
that doc's section 4) — and does not test an adversary deliberately
searching for a flip that evades all checks at once (see that doc's
section 5). It measures weight-bit flips checked against final logits, a
different mutation site than the hash-chain-field example above, so the
two are complementary rather than the same measurement repeated.

## (c) Altered tool result

**What was mutated:** in `m2-changed-tool-result.receipt`, step 0's `out=`
field (the tool's recorded output, hex-encoded) was changed from `3230`
(`"20"`) to `3231`(`"21"`) — a one-nibble edit to the tool's result,
everything else byte-identical to baseline.

**What ordinary logging shows:** here the tampering is visible in the
printed line — `receipt-view`'s `WHAT RAN` section, being a direct,
unverified read of the receipt's own text, faithfully reprints whatever
the file claims:

```
  2 step(s) recorded in the receipt:
    step 0: 16 token(s) decoded, tool=calc, called 'CALC(10 + 10)' -> '21'
    step 1: 16 token(s) decoded, tool=no-tool
```

The important point is not that this specific number is hard to read —
`10 + 10 = 21` is obviously wrong to a human who does the arithmetic — but
that *nothing about the log format itself* flags it. An ordinary
execution log is just text; whoever produced (or edited) the log file
could have written `'20'`, `'21'`, or any other string here, and the log
would look exactly as well-formed either way. Catching this by inspection
requires an external, case-specific check (redoing the arithmetic by
hand); it is not something the logging mechanism itself detects, and for
a tool whose correct output isn't independently known to the reader (most
real tool calls), an altered result would pass unnoticed by inspection
alone.

**What receipt-view shows:**

```
HASH CHAIN
  BROKEN — agent_trace verify rejected this receipt.
  First broken step: step 0
  What changed at that step:
    - the tool's recorded output
  (verifier line: step 0 divergence: toks-match=true tool-match=true in-match=true out-match=false decode-chain-match=true)

VERIFIED OFFLINE: yes — the check ran fully offline and correctly
rejected this receipt (see HASH CHAIN above).
```

Here `agent_trace verify` names the exact field (the tool's recorded
output) that diverges from what replay independently reconstructs, at the
exact step (0) — without needing to know in advance that `21` is
arithmetically wrong. It catches the mutation because the recorded output
no longer matches what replaying the episode against the pinned artifacts
produces, not because it re-did the arithmetic.

**Backing artifact:** `alice-aegis` `demo/agent-trace/receipt-view-fixtures/m2-changed-tool-result.receipt`,
verified via `receipt-view.py` against commit `d9165c0` on host
`aefinity-box`, 2026-09-22.

## What this does not show

- All three cases are single-field mutations chosen to match one fixture
  each in `alice-aegis`'s existing 4-case mutation kit (a 4th case,
  reordering steps 0 and 1, is documented in the same
  `receipt-view-README.md` and is also caught, at step 0; not reproduced
  here since the task only asked for three). None of these are an
  adversary searching for a mutation that evades detection — the larger
  "does the digest ever get fooled" question is what
  `2026-09-13-BITFLIP-HEADTOHEAD.md` and the fuzz/tamper harnesses cited
  there address at scale, not this doc.
- `receipt-view.py` does not itself verify anything — it is a formatter
  over `agent_trace verify`'s own stdout (see `alice-aegis`
  `demo/agent-trace/receipt-view-README.md`, "What this tool does NOT
  do"). If `agent_trace verify` is ever wrong, `receipt-view.py` would
  faithfully report that wrong verdict in plain English; nothing here is
  independent evidence about the verifier's own correctness beyond what
  is measured in `2026-09-13-BITFLIP-HEADTOHEAD.md`.
- Single fixed episode (one two-step calc-tool run), single model
  (pruned BitNet-2B), one machine (`aefinity-box`). No timing claim is
  made or implied anywhere in this document.
- "Ordinary logging" here is represented by `receipt-view.py`'s own
  unverified `WHAT RAN` parse of the receipt file — chosen because it is
  a real, reproducible artifact rather than a synthetic example, and
  because it demonstrates the same property any plain text/JSON agent log
  has (no independent binding between what is printed and what actually
  ran). A specific third-party logging product was not tested.
