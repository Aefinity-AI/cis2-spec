Notes

1. CANDIDATE means a build variant with no pinned expected value. `-DCIS2_REDUCTION_TREE` selects the tree-shaped (non-sequential) reduction order in place of the sequential one; it is the same candidate pinned-tree order as in the P100 result ([`GPU_RESULT.md`](GPU_RESULT.md)), and it is not part of v0.3b. Its digest differs from `CIS2_REF`, which is the expected behaviour of a different reduction order under CIS-2. The host and CUDA tree builds produce the same two digests as each other, and the same two digests as the P100 candidate rows.
2. Host B's C++ source is not part of this tree. Instead of a commit it records the sha256 prefix of the concatenation of `cis2_host.cpp`, `cis2_math.h`, `cis2_model.h`, `cis2_fpenv.h`, `cis2_sha256.h`, `cis2_consts.inc`. Host A built the Rust `cis2_ref` binary from public commit `4240cb1f` (binary sha256 prefix `42be560cd2b67755`).
3. Host A's CPU has SSE4.2 only; host B's CPU has AVX2 and FMA. The host g++ build is compiled with `-ffp-contract=off`, and the CUDA build with `-fmad=false`, so no fused multiply-add is used on either.

## How to add a row

1. Run the verification kit (`kits/`) or `scripts/self_check.sh` on your hardware for `gen_toks=16`, and for `gen_toks=128` where your implementation supports it, against the pinned weights (`scripts/fetch_weights.sh` checks the sha256).
2. Copy the `row ...` and build/toolchain lines from your output. Remove every timing field (`wall_s=...`, durations, throughput) and reduce start/done stamps to dates. Replace hostnames, IP addresses, user names and home paths with a host-class label.
3. Save the cleaned text as `hardware_logs/<tag>_<date>.log` and add one table row per `gen_toks` value to the table above: date, CPU and ISA class, implementation, compiler version, source commit (or source hash), weights sha256 prefix, digest in full, outcome. Use MATCH only when the digest equals the pinned value; use CANDIDATE for a variant with no pinned value; report a mismatch as it is (see `HALL-OF-DIVERGENCE.md`).
